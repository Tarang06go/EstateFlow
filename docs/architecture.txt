1. Purpose and Guiding Principles
EstateFlow manages properties, owners, tenants, rental agreements, rent collection, and maintenance for a small landlord or
property manager.
Principles, in priority order:
1. A finished, tested application beats a large unfinished one.
2. Understanding over magic. Plain JDBC, no ORM, no DI framework. Every line should be explainable in a viva.
3. Proper OOP and layering. Each class has one clear job; dependencies point one way. Abstractions exist only where a real
requirement needs them.
4. One definition for every fact. Derive values (occupancy, charge status, expiry) instead of storing copies that can go stale.
Where a definition must exist in both SQL and Java, it is written down once (Section 6.4) and tested for agreement.
5. Testable by construction. Business rules are pure Java, separated from JavaFX and SQL.
6. Failures are handled once, at the right layer, with the cause preserved. (Section 7)

3.2 Composition root (no DI framework, no static singletons)
AppContext is the only place that constructs AppConfig, DatabaseManager, the transaction manager, DAOs and services, and
wires them together by constructor injection. Controllers receive services through an FXMLLoader controller factory. Nothing is
a Singleton-pattern class; each shared object is created once in AppContext and passed where needed.
3.3 Threading rule
All database work triggered from the UI runs on a background thread through a small UiTask helper (wrapping
javafx.concurrent.Task; it accepts a Callable, so checked exceptions flow to its failure callback). One service call runs
entirely on one worker thread. UI updates happen on the JavaFX Application Thread. UiTask is introduced in Phase 4
together with the first screen.

The mechanism: ConnectionHandle. DatabaseManager.acquire() returns a ConnectionHandle (an AutoCloseable wrapper):
• If a transaction is bound to the current thread, the handle borrows that connection. Its close() does nothing.
• Otherwise the handle owns a fresh connection (auto-commit on). Its close() really closes it.
DAOs always follow one pattern, identical whether or not a transaction is active:
try (ConnectionHandle h = databaseManager.acquire();
     PreparedStatement ps = h.connection().prepareStatement(SQL)) {
    ...
} catch (SQLException e) {
    throw translate(e, "find owner by id");
}
Because closing a borrowed handle is a no-op, a DAO cannot accidentally close a transaction's connection, and no DAO
needs to know whether it is inside a transaction.
Rules
1. Services start transactions only through TransactionManager.inTransaction(TransactionalWork<T>). Services never see a
Connection or ConnectionHandle.
2. A transaction is begun, committed or rolled back on the same thread; its connection is never passed to another thread.
3. Any exception leaving the work (checked, unchecked, or Error) causes rollback; the original exception is rethrown
unchanged. If the rollback itself fails, that failure is attached with addSuppressed (not logged separately).
4. A failed commit surfaces as DataAccessException with the SQLException as cause.
5. Nested inTransaction calls join the outer transaction; only the outermost call commits or rolls back. Work inside a
transaction must never catch and swallow an exception, because the transaction would still commit.
6. Cleanup (unbind, close) happens in a finally block.
7. Single operations outside a transaction auto-commit on their own owned connection.
8. Row locks (SELECT ... FOR UPDATE) are used in exactly two places where a read-then-write check protects money or overlap
integrity: PropertyDao.findByIdForUpdate (agreement creation) and RentChargeDao.findByIdForUpdate (recording a
payment). They are only valid inside a transaction. The locking read must be the first SQL/data-access statement in that
transaction; do not perform a prior plain consistent read that can establish a stale REPEATABLE READ snapshot. After the
lock is acquired, run findOverlapping or the charge-balance/amountPaid query. Do not calculate amountPaid from a subquery
whose rows are assumed locked by an outer FOR UPDATE; any required locking must be explicit. Other validation reads that do
not need transactional state should happen before inTransaction, or after the lock as appropriate. EstateFlow supports one
running application instance at a time, but duplicate Save actions can still create worker-thread races, so the locks remain
necessary.
9. Every try-with-resources on a ConnectionHandle is mandatory; forgetting it leaks an owned connection (code-review item).
10. For each of the two locked flows, Phase 3 integration tests must include a two-thread race test coordinated with latches:
overlapping agreement creation for the same property, and two payment attempts competing for the same charge balance.
Disable the relevant Save action while a UI task is running as a user-interface backstop, not as a replacement for database
locking.
Transactional operations in v1.0: create agreement (lock property, check overlap, insert agreement, insert charges);
terminate agreement (cancel charges, update agreement); record payment (lock charge, validate, insert payment); void
payment is a single update.

5. Domain Model and OOP Design
5.1 Conventions
• Money: BigDecimal, scale 2, RoundingMode.HALF_UP. Never double.
• Dates: java.time.LocalDate / LocalDateTime. "Today" always comes from an injected java.time.Clock.
• IDs: Long, null before insert.
• Models are plain POJOs (no JavaFX properties, no JDBC types). Controllers adapt them for TableView through cell value
factories.
• Where validation lives: services validate user input (through Validators) and throw ValidationException before building or
saving a model. Models only guard against programmer errors (Objects.requireNonNull for required fields,
IllegalStateException for illegal state changes). Models do not re-validate formats or ranges.
• Enums are persisted as VARCHAR using name().
• Read-only query results (joins, aggregates) are Java record DTOs, not models.
• equals/hashCode on entities are based on ID when non-null; toString omits sensitive fields.

6. Database Design (Locked Schema)
6.1 Entity relationships
owner 1 IIII * property 1 IIII * rental_agreement * IIII 1 tenant
                  I                      I
                  I                      1
                  I                      I
                  *                      *
          maintenance_request II(opt)III tenant      rent_charge 1 IIII * payment
• One owner has many properties. Each property has exactly one owner (co-ownership is out of scope).
• A property has many agreements over time; their effective periods may never intersect.
• An agreement has exactly one tenant and many rent charges.
• A rent charge has many payments (this is how partial payments work). Charges are cancelled, never deleted. Payments are
voided, never deleted.
• A maintenance request belongs to a property and optionally references the reporting tenant.

6.3 Schema design rules
• Seven tables. No stored status that can be derived.
• No hard deletes of business records. Owners, tenants, and properties are deactivated (is_active = 0). Rent charges are
cancelled (cancelled_at). Payments are voided (voided_at). All business FKs are ON DELETE RESTRICT (the only exception,
maintenance_request.tenant_id, is SET NULL; since tenants are never deleted this never fires).
• Payment facts (amount, date, method, reference) are never edited. Corrections happen by voiding and re-recording (BR-25).
• INSERT statements for rental_agreement never list effective_end_date.
• due_date is stored separately from period_start (equal in v1.0) so a grace period can be added later without a schema
change.
• Future tables for advanced features (app_user, audit_log) are additive and pre-approved in Section 11. They do not alter
v1.0 tables.

are unchecked and handled centrally. Programmer errors (NullPointerException, IllegalStateException) are never caught to
be hidden.
All EstateFlowException constructors accept an optional cause. TransactionalWork<T> declares throws EstateFlowException.

Logging rules
1. Log where an exception is handled, not where it is thrown or wrapped. DAOs, services, and the transaction manager
do not log exceptions. Expected business failures are shown to the user and not logged.
2. log.error(...) appears only in ErrorHandler and in the startup path of EstateFlowApp. This is grep-checkable and part of
the Definition of Done.
3. Services log successful business events at INFO (for example "Agreement 12 created for property 4"), without personal data
such as phone numbers.
4. A global uncaught-exception handler (default thread handler, plus the FX thread) routes anything that escapes to
ErrorHandler, so nothing is silently lost.
Exception hygiene rules
• Always chain the cause. Never call printStackTrace(). No empty catch blocks.
• Never catch Exception/Throwable except in ErrorHandler and JdbcTransactionManager (which rethrows).
• Use try-with-resources for every ConnectionHandle, Statement, ResultSet, and file stream; use finally only where no
AutoCloseable fits (transaction unbind).
• Messages state what happened and, where possible, what to do, with concrete values: "Payment of I5,000.00 exceeds the
remaining balance of I3,200.00 for the period starting 01 Oct 2026."
• Do not catch an exception inside a lambda just to hide a checked type; validate first, then process.
8. Business Rules (Authoritative List)
These rule IDs are referenced by tests, Javadoc, and commit messages.
Parties and properties
• BR-01 Owner and tenant phone numbers are unique within their table. Normalize phone input before storage and uniqueness
checks by trimming surrounding whitespace and removing formatting spaces, hyphens, and parentheses; preserve a leading
+ if supplied. Tenant ID proof type and number must either both be absent or both be present, and the pair is unique when
provided.
• BR-02 An owner cannot be deactivated while they own an active property. An inactive owner may be reactivated at any time.
EstateFlow Architecture Baseline v1.0 • Revision 4 • FINAL
Page 12
• BR-03 A tenant cannot be deactivated while they have an open agreement (effective_end_date >= today). An inactive
tenant may be reactivated at any time.
• BR-04 A property cannot be deactivated while it has an open agreement. A property may be reactivated only if its owner is
active.
• BR-05 Only active owners can receive new properties; only active tenants and properties can be used in new agreements.
Agreements
• BR-10 An agreement is created from: property, tenant, start date, duration in months (1–120), monthly rent (> 0), security
deposit (≥ 0). The start date may be in the past (to record an existing lease) or the future. Charges for past periods are
generated as due, and historical payments are recorded afterwards in the normal way.
• BR-11 end_date = start_date + duration_months − 1 day.
• BR-12 Effective period. An agreement occupies its property from start_date to effective_end_date inclusive, where
effective_end_date is termination_date if the agreement is terminated and end_date otherwise. This is the only definition
used for occupancy, overlap, deactivation, expiry listing, and effective status. Stored status is not used in date logic.
• BR-13 No overlap. Two agreements for the same property must not have intersecting effective periods (inclusive). The check
runs inside the creation transaction after locking the property row, using AgreementDao.findOverlapping. Back-to-back
agreements are allowed (new start_date = previous effective_end_date + 1 day).
• BR-14 On creation, one RentCharge per month is generated in the same transaction: period i starts at
start_date.plusMonths(i) (computed from the start date each time to avoid month-end drift), ends the day before period i+1
starts, and is due on its period_start. amount_due = monthly_rent.
• BR-15 Termination. Allowed only when the agreement is ACTIVE and today <= end_date (an expired agreement cannot be
terminated). termination_date must satisfy start_date <= termination_date < end_date; it may be in the past (late
record-keeping) or the future (notice period). The operation is rejected if any valid payment exists on a charge with
period_start > termination_date. Otherwise, in one transaction: status = TERMINATED, termination_date is set, and all live
charges with period_start > termination_date are cancelled (cancelled_at). The period that contains the termination date
stays fully chargeable (no proration, D-07).
• BR-16 Agreement terms (rent, dates) are not editable after creation. Only notes may change. Mistakes are handled by
terminating and re-creating.
• BR-17 Occupancy. A property is occupied on date d if some agreement occupies it on d (BR-12); otherwise it is vacant. A
terminated agreement therefore frees the property the day after its termination date.
Rent and payments
• BR-20 Payable charges. A payment can only be recorded against a live charge whose due_date <= today. There are no
advance payments against future charges in v1.0; a period becomes payable on the day it starts. Payable charges are
exactly the charges counted in "outstanding balance".
• BR-21 Payment amount > 0, at most 2 decimal places, and not more than the charge's remaining balance. The balance is
read with RentChargeDao.findByIdForUpdate inside the recording transaction, so the check and the insert are atomic.
• BR-22 Payment date cannot be in the future.
• BR-23 Partial payments are allowed; a charge may have many payments.
• BR-24 Payments can be recorded against payable charges of expired or terminated agreements (to settle arrears).
• BR-25 Incorrect payments. Payments are never edited or deleted. A wrong payment is voided with a mandatory reason
(1–255 characters): voided_at and void_reason are set, the record stays in history, and the payment is excluded from every
balance and total. The correct payment is then recorded as a new payment. A payment cannot be voided twice. Voiding is
allowed on any valid payment, including on terminated or expired agreements. A receipt cannot be issued for a voided
payment. Voided payments appear in the ledger and payments report with status VOID.
• BR-26 Derived values follow Section 5.4 exactly. "Today" comes from the injected Clock.
• BR-27 Lease-expiry warning window is configurable (lease.expiry.warning.days, default 30).
Maintenance
• BR-30 Requests can only be opened for active properties; a tenant, if given, must have (or have had) an agreement on that
property. reported_date cannot be in the future.

14. Change Control (Architecture Lock)
Locked (requires a change request): technology stack (Section 2); layer rules (3.1); connection and transaction rules (3.4);
database schema (Section 6); exception hierarchy and handling policy (Section 7); business rules (Section 8); class
responsibilities (Section 9); package structure at the top level (Section 4).
Free to change without a request: private methods and internal helpers, FXML layout and CSS, validation message
wording, additional tests, additional non-public helper classes inside an existing package, performance tuning that does not
alter schema or behavior.
Change request process
1. Write docs/change-requests/ACR-NNN.md containing: problem, why the baseline cannot handle it, proposed change, affected
classes/tables/rules, effort and risk, and alternatives considered.
2. Approve explicitly, then update this document: bump the version (v1.1, v1.2 …) and add a changelog entry.
3. Implement after the baseline is updated, never before.
Additive changes already listed in Section 11 still follow steps 1–3 but are considered pre-reviewed.
Out of scope for v1.0 (not a change request; simply not built): multiple tenants per agreement, co-owners, late fees and
grace periods, rent escalation and renewals, advance/credit payments, security-deposit refunds, utilities billing, document
uploads, notifications/email, multi-currency, multi-user concurrent access, cloud sync, online payment-gateway processing
and webhook verification. Payment methods such as UPI/card are recorded as externally completed payments; v1.0 does not
initiate or verify a live transaction.

15. Definition of Done for v1.0
• All features in Section 9 work through the UI against MySQL.
• Every business rule BR-01–BR-32 has at least one automated test.
• DAO, transaction, and key service-flow integration tests pass against estateflow_test; the test harness refuses non-_test
schemas.
• Race tests prove agreement overlap prevention and payment overpayment prevention under two concurrent worker threads.
• JaCoCo reports coverage; line coverage is at least 70% for service, service/rules, model, and report (guideline in Phase 7).
• No layer-rule violations (no DAO/SQL in controllers; no javafx.*, db.*, or java.sql.* in services; db may depend only on the
specific dao transaction interfaces as stated in Section 3.1).
• No database calls on the JavaFX Application Thread.
• log.error appears only in ErrorHandler and the EstateFlowApp startup path; no printStackTrace, no empty catch.
• No DAO calls commit, rollback, setAutoCommit, or close on a Connection.
• Every DataAccessException retains its SQLException cause; the UI never shows technical database text.
• Clean clone → documented setup → running app with seed data in under 15 minutes.
• README includes screenshots, ER diagram, architecture diagram, and run/test instructions.
• Git history is clean, tagged v1.0.
